# 扫描任务运营工作台设计说明

**日期：** 2026-08-28
**范围：** 登录后的 `/tasks` 扫描任务列表页；不包含创建页、详情页、接口或权限规则改动。

## 目标

把现有“能筛选的任务表格”提升为面向日常运行的任务工作台：管理者或执行者先辨认当前查询的执行态势和需关注任务，再进入可追溯台账处理具体任务。

页面保持高级雾灰浅色体验，并继续随现有 Fluent 主题（浅色、深色、系统）自适应。它不能把当前页的数据伪装成全量运营统计，也不能改变已存在的服务端筛选、分页、角色权限和真实状态语义。

## 已确认的产品取向

采用“运行态势 + 异常待办 + 可追溯台账”的组合：

1. **运行态势优先。** 首屏先说明当前筛选范围、服务端匹配总数，以及当前页中正在执行、等待调度、需关注任务的数量。
2. **异常可见但不喧宾夺主。** 失败、调度失败和调度待确认作为“需关注”；执行中和等待调度使用克制的中性/品牌语义，不制造虚假的完成感。
3. **台账仍是事实来源。** 用户仍通过精确筛选、分页和“查看”进入详情。不能添加前端排序、客户端过滤、批量操作、自动重试或任何写入行为。

## 数据与真实口径

只使用已通过 `fetchTaskList` 白名单解析的 `TaskListResponse`：

| 页面信息 | 数据来源 | 呈现规则 |
| --- | --- | --- |
| “匹配任务”总数 | `query.data.total` | 明确表示为当前服务端筛选下的总数。 |
| 当前页任务数 | `query.data.items.length` | 仅作为状态条的分母或说明，不外推至所有页。 |
| 正在执行 | 当前页 `dispatching` 与 `running` 数量 | 文案必须带“本页”。 |
| 等待调度 | 当前页 `pending` 数量 | 文案必须带“本页”。 |
| 需关注 | 当前页 `failed`、`dispatch_failed`、`dispatch_unknown` 数量 | 文案必须带“本页”。 |
| 状态、类型、负责人、更新时间 | 每条 `TaskSummary` | 保持现有服务端数据、时间格式与任务详情链接。 |

`succeeded` 与 `cancelled` 是终态台账信息，不被计入“正在执行”或“需关注”。本次不计算完成率、平均耗时、风险级别、全局状态比例或任何 API 没有返回的数值。

## 信息架构与视觉层级

页面自上而下由四层组成：

1. **页头。** 保留“扫描任务”和创建任务入口；说明改为运营语境，仍明确筛选由服务端在分页前执行。
2. **查询上下文。** 一个轻量雾灰面板概括“当前查询”，显示精确筛选标签（全部或已选状态/类型）和服务端 `total`。仅当 URL 实际带有筛选时提供“清除筛选”按钮；按钮调用既有查询参数规范化路径回到第 1 页。
3. **本页运行态势。** 仅在列表成功且有项目时显示三项紧凑信号：正在执行、等待调度、需关注。每项直接标注“本页”，使其和查询总数的范围不可混淆。需关注使用现有主题的警示色，其他两项使用中性/品牌令牌。
4. **任务台账。** 保留原生 `table`、caption、列标题、分页和查看链接。将状态文本包裹在语义化状态标记中，表格容器只在自身横向滚动，不让整页在窄屏横向溢出。类型、负责人、状态、更新时间和操作列保持原有顺序与事实来源。

窄屏（960px 以下）下，查询上下文、筛选和运行态势改成单列；表格保留局部横向滚动。页头创建入口不丢失，筛选控件可全宽使用。大屏布局在过滤器与查询上下文之间保持清晰留白，不引入卡片墙或装饰性图表。

## 组件边界

新增一个本地、纯展示的 `TaskOperationsSummary` 组件，并将状态派生函数与类型同置：

- **输入：** 已校验的当前页 `TaskSummary[]`、服务端 `total` 和由 URL 正常化后的已选筛选。
- **输出：** 具名“任务运行态势”区域；内部的“当前查询”与“本页信号”使用组语义，不嵌套额外 landmark。
- **职责：** 只派生本页三类状态数量和展示筛选上下文；不发请求、不改变 URL、不决定角色权限。

`TaskListPage` 保持查询、URL 参数、状态分支、创建权限、表格列和分页职责。它在获得成功数据后把安全 DTO 传给展示组件，并且继续让加载、错误、403、空态相互独立。

状态标记可以作为 `TaskListPage` 内的局部渲染器，或成为同目录只读展示组件；无论形式如何，必须从既有 `taskStatusLabels` 获取中文标签，不能重写或放宽状态白名单。

## 状态与权限

- **加载、403、失败：** 不显示查询总数或本页运行信号；继续使用既有 `StatePanel` 文案与显式重试行为。
- **空结果：** 显示现有“暂无匹配任务”状态；保留筛选上下文和清除筛选入口（若存在），不显示零值态势卡，避免将空结果误读为全部健康。
- **普通用户和管理员：** 保留创建任务入口。
- **审计员：** 保持只读，不出现创建入口；本次不改变详情页取消/下载授权。
- **敏感数据：** 继续只渲染 `TaskSummary` 已有白名单字段；`input_summary` 或服务端的额外字段不得进入此页 DOM。

## 无障碍与主题

- 查询上下文、运行态势和筛选都需具名语义，原生表格 caption 和每条“查看任务 {id}”链接保持不变。
- 状态不能仅凭颜色区分，必须保留完整中文状态文字与“本页”范围说明。
- 所有新表面、边框、文字、阴影和状态颜色使用 Fluent tokens；不写死仅适合浅色模式的颜色。
- 可交互的清除筛选、创建任务、上一页、下一页和查看链接必须具有可见焦点。

## 非目标与不可变约束

- 不改 `fetchTaskList`、任务 DTO 解析器、URL 参数协议、API 地址、查询 key 或重试策略。
- 不改 `TaskCreatePage`、`TaskDetailPage`、侧栏、顶栏、全局主题或共享 `DataTable` 的公共 API。
- 不添加搜索、日期范围、批量操作、导出、排序、任务写入、自动轮询或模拟指标。
- 不触碰工作区中预先存在、未跟踪的 `.superpowers/` 目录。

## 验证策略

在现有 `TaskPages.test.tsx` 中扩展列表覆盖，至少验证：

1. 成功列表中存在具名查询上下文和任务运行态势，且三类“本页”数字由包含 `pending`、`dispatching`、`running`、失败类、终态的 fixture 精确派生。
2. `total` 与当前页数量被明确区分，禁止把本页状态计数误呈现为全局数值。
3. URL 带筛选时出现清除筛选入口，点击后只用已有 URL 正常化方式回到第 1 页并发送无筛选请求；无筛选时不出现该入口。
4. 既有原生表格、审计员只读、URL 恢复、恶意参数归一化、加载/错误/403/空态以及详情链接断言继续通过。
5. 在窄屏 CSS 断点下，主要容器和台账 viewport 没有固定最小宽度造成页面横向溢出；表格的局部滚动可保留。

完成实现后运行任务页定向 Vitest、`pnpm run lint`、`pnpm run typecheck`、`git diff --check` 和前端 Docker 全量门禁。浏览器验收时检查 390px、1280px 两种视口的成功与空态，并确认登录后 `/tasks` 可达。
